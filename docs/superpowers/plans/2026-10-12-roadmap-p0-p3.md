# 求职系统 P0–P3 路线图

日期：2026-10-12（修订：同日，按用户意见移除所有 AI agent 调用）。代码基线：`695e245`（Initial commit）。
本文是 P0–P3 的范围、设计决定和验收标准，也是 [P0 详细实施计划](2026-10-12-p0-linux-screening-worker.md) 的 spec。P1–P3 各自在开工前再写一份同样粒度的详细计划，因为它们的接口取决于 P0 落地后的实际形状。

前一份方案 [docs/reviews/2026-10-09-job-agent-proposal.md](../../reviews/2026-10-09-job-agent-proposal.md) 仍是长期设计参考；本文按"先让每天收到的岗位真正可用"重新排了优先级。

**分工（用户确认，2026-10-12）**：本系统只负责**确定性**的部分：采集、补全 JD、规则筛选、推送、记录和接口。**所有 AI agent 相关的工作由用户自己安排**，包括 LLM 筛选、Claude Agent SDK、简历生成，以及用 computer use 注册账号、投递。原因是这些工作消耗额度，指令也由用户自己给。系统不内置任何模型调用，只给 agent 提供可以读取和回写的接口。

## 1. 目标

**求职目标**

- 所有 **new grad / entry level** 岗位，**泛 CS** 方向（软件、数据、ML/AI、基础设施、安全、嵌入式、量化开发、QA、IT 等）。
- **不要实习**（intern、co-op、apprenticeship）。
- **优先有签证担保（visa sponsorship）的岗位**；不提供担保的也保留，只是排序靠后。
- 推送渠道：**Discord**。

**系统目标**

| 优先级 | 能力 | 是否必须 |
|---|---|---|
| P0 | 在 Linux 上自动收集 → 补全 JD → 规则筛选 → Discord 推送（不调用模型） | 必须 |
| P1 | 采集覆盖更全（公司 ATS、邮件提醒）；能在 Discord / Grok / Dot 里**管理**，而不只是查询 | 必须 |
| P2 | 给你的 computer-use agent 用的投递接口：投递队列、投递资料包、结果回写、账号登记、护栏 | 可选 |
| P3 | 投递后状态跟踪、git 部署、备份、健康告警 | 长期稳定运行需要 |

## 2. 现状基线（2026-10-12）

- Linux（`home-ubuntu`）：`auto-app-ingest.service` 每 30 分钟拉取 10 个 GitHub 职位仓库；库里约 **10,219 个岗位，全部 `not_evaluated`，`jobs_with_description: 0`**。
- 通知 `src/auto_app/core/notify.py` 只支持 macOS；Linux 上只写日志。
- MCP + OpenAI Secure Tunnel → Dot 可用：4 个查询/记状态工具，外加一个用虚构身份预填 Ashby 表单的工具。
- 申请链接分布（7,840 条样本）：Workday 34%、其他 31%、Greenhouse 11%、Ashby 6%、Oracle 6%、iCIMS 4%、Lever 4%、SmartRecruiters 3%。**约 55% 落在项目已有适配器的平台上**（Workday/Greenhouse/Ashby/Lever）。
- 现有的 LLM 筛选（`auto-app filter run`）会跳过没有 JD 的岗位（`src/auto_app/select/engine.py:84`），所以 Linux 上目前没有任何岗位被筛选过。
- Mac 本地没有 `config/searches.yaml`、`filters/`、`profile/`，也没有数据库。
- 10-12 修复的 15 个问题还没部署到 Linux（Linux 上的代码停在 10-11 的快照）。

## 3. 目标架构

Linux 是唯一主节点：唯一的数据库、唯一的调度、唯一的对外接口（MCP）。Mac 只用于开发和部署。

```text
GitHub 职位仓库 ─┐                          ┌─ Discord（P0 webhook 推送；P1 bot：按钮 + 斜杠命令）
公司 ATS（P1）  ─┼─► ingest worker ─► SQLite ◄─► worker：screen → enrich → screen → notify（无模型调用）
邮件提醒（P1）  ─┘     （已有）          ▲
                                         ├─ MCP server ─┬─ OpenAI tunnel → Dot（已有，loopback 无认证）
                                         │              └─ 认证 HTTPS（P1）→ Grok / 你的 agent
                                         └─ 你自己安排的 agent：LLM 筛选（filter run）、简历、computer-use 投递
```

各阶段共同遵守的原则：

1. **规则排除是"视图"，不是决定**：不删岗位、不改 `step2`/`decision`，改规则后下一轮就恢复可见；被排除的岗位带原因，可以审计。
2. **只有明确证据才排除**；不确定的一律保留，交给你（或你的 agent）判断。
3. **系统内不调用模型或 agent**；所有 agent 都通过 CLI / MCP 接口读写数据，接口在服务端做校验。
4. **密钥不进仓库，也不进数据库**：Discord webhook、bot token、MCP token 放在 Linux 的 `runtime/credentials/`（权限 600），通过 systemd `EnvironmentFile` 注入；网站账号密码只放在密码管理器里。
5. **对招聘网站有礼貌**：只用公开 API，每个 host 请求间隔 ≥1 秒，每轮请求数有上限；不做 LinkedIn 免登录抓取。

## 4. P0：让岗位真正流到你面前（详细计划已写）

详细计划：[2026-10-12-p0-linux-screening-worker.md](2026-10-12-p0-linux-screening-worker.md)。

**交付**：新的 `auto-app worker` 进程（systemd 用户服务，每 15 分钟一轮），每一轮依次执行：

1. **screen（规则筛选）**：按标题、雇佣类型、来源、仓库标签（Simplify 的 sponsorship/category）和 JD 文本，给每个活跃岗位标记 `kept` 或 `excluded`，并写明原因。规则写在 `runtime/config/screening.json`，默认如下：
   - 排除实习：标题含 intern/co-op/apprentice；季节性标题（如 Summer 2027）且不是 new grad；雇佣类型为 internship；只出现在实习 feed 里。
   - 排除高级职位：senior/sr/staff/principal/lead/manager/director/architect、III 及以上级别。标题含 new grad/entry/junior 时不触发。
   - 排除明确的非 CS 岗位：机械、土木、芯片设计、销售、市场、HR、财务、产品/项目经理等。标题同时命中 CS 词时保留。
   - 排除明确要求美国公民身份、安全许可或 ITAR "U.S. person" 的岗位。**（假设你需要签证，请确认）**
   - 排除 JD 明确要求 ≥3 年经验的岗位（"preferred / nice to have / in lieu of" 这类表述不算）。
   - 雇主 API 返回 404 的岗位标记为已关闭。
   - **签证担保只作为信号**（offers / no / unknown / citizenship_required），用来排序，不用来排除。
2. **enrich（补全 JD）**：对规则保留的岗位，按申请链接调用 Greenhouse/Lever/Ashby/Workday 的公开 API 取 JD，复用现有平台解析器。结果按 URL 缓存；失败按指数退避重试，从 30 分钟开始，上限 24 小时。
3. **screen again**：JD 补全后再跑一次规则，因为经验年限、公民身份、担保信号都依赖 JD。
4. **notify（Discord 推送）**：推送规则保留、你还没处理、没被你自己的筛选器判为不推荐的**新岗位**。排序：有担保 → 未写明 → 无担保；同一组里，你的筛选器推荐过的（⭐）排在前面，然后按发布时间从新到旧。
   - 没有 JD 的岗位先等 2 小时补全，之后以"仅标题"推送。
   - 只有 Discord 确认收到后才标记已通知。
   - 首次部署前的存量岗位不推送（在聊天里查），避免刷屏。
   - 失败告警：同一问题 12 小时内只发一次。

另外：

- 查询接口和 MCP 的 `search_jobs` 默认隐藏规则排除的岗位，新增 `sponsorship` 过滤参数，`get_job_context` 返回规则统计。
- 现有的 `auto-app filter run` 自动跳过规则排除的岗位。你按额度手动跑 LLM 筛选时，不会浪费在明显不合适的岗位上。
- Linux 上停用 4 个实习 feed。部署前自动备份数据库。

**验收**：

- Linux 上 `auto-app worker status` 显示每 15 分钟一轮成功；`get_job_context().screening` 显示 kept/excluded 计数和排除原因分布。
- 规则保留的岗位里，申请链接属于四个支持平台的，24 小时内补全 JD 的比例 ≥90%。
- 新岗位在 15 分钟内推到 Discord（没有 JD 的最迟 2 小时 15 分钟）。按担保排序，每条带职位、公司、地点、担保情况、备注和申请链接。
- 在 Dot 里问"有哪些提供签证担保的新岗位"，能通过 `search_jobs(sponsorship="offers")` 得到结果。
- 抽查 30 个被规则排除的岗位，误排除 ≤2 个（不达标就调规则）。

## 5. P1：采集覆盖 + 在聊天里管理

### P1.1 公司 ATS 采集搬到 Linux

- 现有的 Greenhouse/Lever/Ashby/Workday 公司插件是纯 API，不需要浏览器。在 worker 里加一个 `collect` 步骤：调用现有的 `run_pipeline(..., collect=True)`，只跑公司来源，带时间上限。
- 公司列表：从 GitHub 仓库里出现频率最高、提供担保比例最高的雇主开始（数据已经在库里，可以直接统计），用 `auto-app source add` 批量生成插件，每家公司一个 `new-grad` 搜索。
- 验收：至少 30 家公司的官网岗位每天进库，和仓库来源的同一岗位正确去重（同一 employer key）。

### P1.2 邮件提醒（LinkedIn / Jobright / Handshake）

- 新增 `kind: mailbox, provider: imap`：Gmail 用应用专用密码（app password），复用现有的 `mail_messages` 收据表和 `parse_email`。凭据放 `runtime/credentials/imap.json`（权限 600）。
- LinkedIn 链接拿不到 JD（不做免登录抓取），这类岗位只能按标题规则筛选，Discord 里标"仅标题"。如果以后想要 JD，可以让 Mac 上已有的 LinkedIn 浏览器采集器（用你的真实登录）把结果推到 Linux。要不要做由你决定。
- 验收：一封 LinkedIn 岗位提醒邮件里的岗位 30 分钟内进库，不重复导入，不改变邮箱的已读状态。

### P1.3 MCP 加认证，接入 Grok 和你的 agent

- 现有的 loopback 无认证监听保持不变，继续给 OpenAI tunnel → Dot 用。
- 新增**第二个监听**：Streamable HTTP + Bearer token（或 OAuth，取决于 Grok 支持哪种），只通过 Cloudflare named tunnel 或 Tailscale Funnel 暴露到公网。不要用 quick tunnel，它不支持 SSE。
- Grok 的自定义连接器要求公网可访问的 URL，会拒绝 localhost 和内网地址，认证在 Grok 里完成（[xAI 文档](https://docs.x.ai/grok/connectors)）。有用户反馈 Grok Bot 的远程 OAuth 流程会失败（[论坛](https://forum.cursor.com/t/grok-bot-custom-remote-mcp-oauth-never-starts-fetch-failed-same-url-works-in-cursor-ide/168188)），所以 P1 详细计划的第一步是做一个最小的认证 MCP 端点，实测 Grok 能用哪种认证。
- 同一个认证端点也给你的 computer-use agent 用（P2 的投递工具挂在这里）。
- 验收：在 Grok 里能调用 `get_job_context` 和 `search_jobs`；不带 token 的请求返回 401；轮换 token 不需要改代码。

### P1.4 MCP 控制类工具

在现有 4 个工具之外新增。全部在服务端校验，不暴露 shell、SQL 或任意文件写入：

| 工具 | 作用 |
|---|---|
| `get_pipeline_status` | ingest 和 worker 的上次/下次运行、失败次数、各来源健康状况 |
| `pause_pipeline` / `resume_pipeline` | 暂停/恢复 worker（可指定截止时间），返回服务端确认后的状态 |
| `get_screening_rules` / `propose_screening_change` / `apply_screening_change` | 读规则。提出修改时返回 diff 和预演结果（会新增/减少多少岗位）；你确认后，带 change_id 和 revision 才能写入 |
| `record_filter_feedback` | 记录"这个不该推荐"，写入现有的 feedback 表 |
| `get_digest` | 返回和 Discord 推送同样内容的增量摘要（给 Dot/Grok 用） |

### P1.5 Discord bot（双向，不含 AI）

- P0 的 webhook 升级为 bot（`discord.py`），仍在 Linux 上运行。
- 推送消息带按钮"想投 / 跳过 / 已投"，点按钮直接调用现有的 `record_application_status`。
- 斜杠命令：`/jobs`（支持担保、公司、关键词过滤）、`/job 123`、`/status`、`/pause`、`/resume`。
- 不做自由对话。如果你想在 Discord 里和 agent 对话，由你自己接 agent，用的是同一个 MCP。
- 只响应你的 Discord 用户 ID；bot token 放在 `runtime/credentials/`。
- 验收：手机上点"想投"之后，在 Dot/Grok 里查到同一个岗位已经是 `want_to_apply`。

## 6. P2：给你的 computer-use agent 用的投递接口（可选）

你打算用 computer use 自动注册账号、参与投递，agent 的指令和额度由你安排。系统这边只提供 agent 需要读取和回写的东西，并在服务端加护栏。

**接口**（CLI + P1.3 的认证 MCP，两者共用同一个服务层）：

| 工具 | 作用 |
|---|---|
| `get_application_queue` | 按你的顺序返回 `want_to_apply` 的岗位：申请链接、平台、JD、担保信号、重复投递警告 |
| `get_application_packet(job_id)` | 投递资料包：JD 快照、申请链接、非敏感的个人资料字段（来自 `runtime/profile/`）、已登记的简历文件路径和 hash |
| `claim_application(job_id)` | 领取一个岗位，带租约，避免两个 agent 同时投同一个；租约过期自动释放 |
| `record_application_attempt(job_id, outcome, note, evidence)` | outcome ∈ `submitted / needs_user / blocked / failed / skipped`。`submitted` 时把岗位标为 `applied`，记录"由 agent 提交"，和你手动标记区分开；evidence 是确认页截图路径或确认邮件 ID |
| `record_site_account(site, email, created_by_agent)` | 写入现有的 `accounts` 表：站点、邮箱、是否由 agent 创建。**不存密码** |
| `register_resume(job_id, path)` | 登记你的 agent（例如你的 `jd-resume-tailor` skill）生成的简历：路径、sha256、生成时间 |

**服务端护栏**（agent 绕不过去）：

- 已投、已归档、被规则排除、或"疑似重复投递"（现有的 repost 警告）的岗位，不进投递队列。
- 每日投递上限，以及同一公司的冷却期（例如 30 天内最多 3 个），都写在配置里。
- 同一岗位只能有一个有效的 `submitted` 记录。

**给你的 agent 的建议**（由你写进指令，系统不内置）：

- 网站账号密码用密码管理器（如 Bitwarden / 1Password 的 CLI）生成和保存，不要写进数据库、聊天记录或日志。
- 遇到验证码、邮箱验证、短信验证时停下，返回 `needs_user`，系统会推到 Discord 通知你处理。
- 工作授权、签证、薪资期望、EEO 这类问题，答案固定写在 `runtime/profile/` 里，agent 只读不猜。

**注意**：仓库的 `CLAUDE.md` 目前写着"Never submit a job application"。这条规则约束的是在这个仓库里工作的 Claude Code 会话。如果你希望在这个仓库里运行的 agent 也能投递，需要你自己修改这条规则；我不会擅自改它。

**验收**：用一个测试岗位走完一遍完整流程：领取 → 资料包 → 回写 `submitted` → 岗位变成 `applied` → Discord 收到"已投递"通知。护栏能拒绝重复投递和超出每日上限的投递。

## 7. P3：长期稳定运行

- **投递后跟踪**：新增 `application_events`（applied / OA / interview / rejected / offer / withdrawn）。来源有：手动（聊天、Discord 按钮）、P2 的 agent 回写、邮件识别（IMAP：申请确认、拒信、面试邀请，用规则匹配）。每周在 Discord 发一次汇总。
- **git 部署**：在 Ubuntu 上建私有 bare repo（或者用私有 GitHub 仓库）。部署脚本：拉取指定 tag → `uv sync --frozen` → 备份数据库 → 显式运行迁移 → 重启服务 → 健康检查。不再用 tar 包快照。
- **备份**：systemd timer 每晚用 SQLite online backup 备份 `auto_app.db` 和 `preparation.sqlite3`，保留 14 份每日备份和 8 份每周备份，并复制一份到 Mac 或云盘；每月自动做一次恢复测试（用 QueryService 打开备份）。
- **健康告警**：每个服务配 `OnFailure=` 钩子发 Discord 消息；worker 发现某个来源连续失败或磁盘空间不足时告警。
- **收敛**：README 里 Mac launchd/TUI 部分标记为"开发用"，不再加新功能。

## 9. 风险

- **推送量**：没有 LLM 这一层，规则保留的新岗位会全部推送。估计每天几十到一两百条，每轮最多推 30 条，其余顺延到下一轮。如果太多，可以收紧规则；也可以等 P1.5 加一个"只推有担保的"开关。
- **初次积压**：规则保留后估计还有约 3,000 个岗位，补全 JD 大约需要 4 小时（每轮 200 个请求）。这些存量不推送，可以在聊天里查。
- **规则误排除**：正则不可能完美。排除是可逆的、带原因的；验收里有抽查；规则文件可以随时改，下一轮就生效。
- **ATS API 变化**：四个平台的公开 API 不保证稳定。失败会退避重试，不影响其他步骤；连续失败会告警。
- **SQLite 并发写**：ingest worker 和新 worker 写同一个库。写事务都很短，并且有 5 秒 busy_timeout；万一冲突，该步骤报错，下一轮重试。
- **自动投递（P2）**：大量自动投递可能触发 ATS 的风控，或违反部分网站条款。服务端的每日上限和公司冷却期是为此设的；具体策略由你决定。

## 10. 不做的事

- 系统内不调用模型或 agent（不用 Claude CLI、Agent SDK、API key）。
- 不做多用户、不迁移 PostgreSQL、不引入消息队列。
- 不做 LinkedIn 免登录抓取，不绕过验证码或反爬机制。
- 不在数据库、日志或聊天里保存任何网站密码。
